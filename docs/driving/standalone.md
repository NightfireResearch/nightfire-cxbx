# The standalone driving engine

Every driving function is ours (tools/function_coverage.py --driving: only exception funclets live), but the build
still runs inside the original image: driving.exe maps Driving.xbe at 0x10000 and drivinginject.dll writes a jump at
each FUNC_AT address. The goal is a build that compiles from our C/C++ alone and runs with no original code or data
mapped. This page is the preparation (13 October 2026): the test modes that show what still touches the image, the
audit of the addresses left in the source, what this round made ours, and the standalone target whose compile errors
are the remaining worklist. Tested on 13 and 14 October 2026: see [Test results](#test-results-13-14-october-2026)
for what the modes found and what was fixed. The game data moved into our source on 14 October 2026 (below).

**Since 14 October 2026 the standalone executable links and runs** (`driving_standalone`, and
`driving_standalone_test` with the lockstep harness): nothing of Driving.xbe is mapped or read, and its lockstep runs
match the injected build's baselines exactly on all eight missions. See [The standalone
executable](#the-standalone-executable-14-october-2026) at the end.

## The game's data: in our source, checked against the XBE by hand

The build needs neither Driving.xbe nor any Python package: it runs only tools/preprocess.py, which reads committed
files. Since 14 October 2026 (branch driving-standalone-data) the game's tables are typed initialisers in our source;
the first round of the prep had taken them from the user's XBE at build time (an `extract_driving_data` target and
`XBE_INITIAL`), which left CI, with no disc, unable to build.

| What | Where | How |
|---|---|---|
| The tuning tables (41 at first) | beside their code: particle types, weapon systems, refire times and selection order, soft zones, muzzle flash tables, light types, needle ranges, camera constants, damage levels, the BondCar surface tables, both hands' IK, the weapon instance matrix, the EMP vectors, `SimStep`, the FX bus modes, the debris vectors, the I3DL2 listener presets, the bank names | aggregate initialisers with our structs; floats as decimals that round-trip (or `std::bit_cast` of the word where the original's is odd) |
| The EAGL shaders | eagl/EaglFont.cpp, eagl/RenderMethod.cpp; the formats in gfx/D3D8Shaders.h | the vertex declarations with `D3DVSD_*`; the three vertex programs in the XDK's assembly (`Dp4(oPos.x(), v(0), c(0))`, ...) assembled to NV2A words at compile time (`Vsh::Function`); the pixel shaders as `D3DPixelShaderDef` (D3DPIXELSHADERDEF) with the XDK's `PS_*` encodings. The D3D9 backend translates those words to shader bytecode at run time (nv2aPixelShader.cpp, nv2aVertexShader.cpp), so it needs them as input: it does not recognise programs |
| EAGL's built-in SHPX | eagl/Tar.cpp, `BuiltInShapeFile` in eagl/Realgraph.h | the header, the 64x64 DXT1 image "fail" and its six mipmaps as `DxtBlock` rows, the 'i' and 'p' attachments |
| The sound mixer's tables | sound/snd/Platform.cpp, Voices.cpp, Decode.cpp | kept as blocks in the original's order wherever a read goes past a table (`VolumeLowpassTables`, `PanReverbTables`, `XaTables`); the EA-XA nibble values (signed nibble x 2^(12 - shift)) are computed at compile time; the volume, pan and low-pass tables follow no formula we could match, so they are written out |
| The Girl palette | game/GirlPalette.cpp | 128 x 128 signed RGB, written out (an image) |
| The vtables and event tables | src/driving/Vtables.h/.cpp | written once by `tools/driving_data_check.py --vtables`: each game vtable the source names, each slot the injection table's port of that original |
| The shadow tests' owned-globals table | src/driving/devtools/OwnedGlobals.inc | committed; `python tools/owned_globals.py` regenerates it (XBE, capstone), `--check` says whether it is current |
| The original code's map | src/driving/devtools/autogenerated_code_map.inc | generated by tools/preprocess.py from tools/code_ranges_driving.txt |

The DSP effects image is gone: our DirectSound has no DSP, and its `DownloadEffectsImage` ignored the image, so
`SNDPLATFORM_init` no longer downloads it (original-quirks.md 1.3, sound.md 5.1).

`python tools/driving_data_check.py` (by hand; the XBE, the built Release/drivinginject.dll and its .map) checks it all:

- every owned global with an initialiser is found in the DLL through the map and its bytes compared with the XBE's at
  the tagged address. A word the DLL relocates is a pointer of ours: it matches when the XBE's word points at the
  same text, or at the game's copy of the owned global or vtable ours points at; code pointers are counted, not
  compared. Globals in .bss (their game value comes from the static initialisers) are skipped, and the few with
  internal linkage the map cannot see are listed. `ALLOWED` in the script names initial values ours on purpose.
- Vtables.h/.cpp are regenerated in memory and compared.

First run (14 October 2026): 308 of 357 initialised owned globals match, 44 in .bss, 5 not checked (two function
statics both named `scale` in anim/IK.cpp, three file statics), and one real difference found: `FeatureDefault50`
(0x001c4820) was our `int32_t` 1 where the XBE holds 1.0f, copied raw into `FeatureManagerData::unknown50`, which
nothing reads. It is a float 1.0f now. Mutations are caught: that one was.

`tools/code_map.py` (capstone; its output tools/code_ranges_driving.txt is committed, like abi_driving.json) walks
every function and every patched address for the bytes that are instructions.

## Test modes

All in `src/driving/devtools/StandaloneTraps.cpp`, off unless their variable is set; for lockstep runs
(`NIGHTFIRE_LOCKSTEP=1 NIGHTFIRE_SNDLOCKSTEP=1`, docs: lockstep-runs) **without shadow tests** - the trap refuses to
start, and says so, when any `NIGHTFIRE_*SHADOW*` variable or `NIGHTFIRE_RESTORE_RANGES` is set, since those run
originals on purpose.

| Variable | What it does | What to look for |
|---|---|---|
| `NIGHTFIRE_TRAP_ORIGINAL=1` | at the end of `Inject()`, every instruction byte of the original code (the code map) that no patch wrote becomes int3. The patches are found by comparing the code with a copy taken at the start of `Inject()` | any execution of original code is an int3: the loader now reports EXCEPTION_BREAKPOINT as a fault (crash.log names the callers, crash.dmp) |
| `NIGHTFIRE_TRAP_ORIGINAL=2` | the same, and the patches over function entries too, except the entry point's (the loader calls 0x0010e777) | every call through an original's address - a table, a callback, a thread entry, a by-address call - faults: the worklist for code pointers |
| `NIGHTFIRE_TRAP_DATA=1` | from the first simulation tick (devtools/Teleport.cpp), every page of .rdata/.data/.bss (0x00189be0-0x0024b5bc) is a guard page; each touch is recorded and the page re-armed after the instruction by a single step. Distinct (code, data, kind) with counts go to `NIGHTFIRE_TRAP_DATA_FILE` (default `trap_data.txt`), rewritten every 10 s and at exit; the code address is ours, or for an access inside the runtime or the host the first return address into our DLL ("via") | `python tools/trap_data_summary.py trap_data.txt` groups them by global (our source's names for the game's addresses, and the owned ones' tags) with the sites |
| `NIGHTFIRE_TRAP_DATA=2` | the same from the end of `Inject()`, so the startup and the static initialisers are logged | |
| `NIGHTFIRE_HEAP_SHIFT=<bytes>` | at the start of `Inject()` the shift's whole 64 KB units of address space are reserved, so everything allocated bottom-up afterwards (the process heap's segments, contiguous memory, the pools) lands elsewhere; the remainder is a block allocated first in the process heap (XboxStartup.cpp's one guarded call), moving every heap address | a lockstep run with it should match the baselines frame for frame and in the sound trace; a difference is behaviour that depends on pointer values (address sorts or hashes, the catalogued uninitialised-memory quirks): a finding for the standalone build |

Caveats: TRAP_DATA misses a touch another thread makes in the one instruction its page is unguarded, and a system call
given a buffer in a guarded page fails rather than faulting (none is known: the file and sound buffers are heap
blocks). TRAP_ORIGINAL cannot fill code no entry reaches (an original Ghidra never made a function that nothing
patches): the audit lists the ones the source names.

## The shadows after the prep

Owning 145 more globals broke about 40 of the shadow tests (every run of the first full round died in the loader's). They were
written while the game's copy was the only one: the port and the originals worked on it, and the shadows set inputs
and read results by its address. The fixes, in devtools and tools/owned_globals.py:

- **One copy again for the prep's globals.** owned_globals.py marks them SINGLE_COPY (the mutable ones; not the
  constant tables, the code tables, or `ClassMemory`, which the originals index past its 16 entries). Like EAGLAnim's
  allocator state before them they are *shared*: from the first original window on, every original instruction that
  names one - found by a capstone scan of the code map, not only Ghidra's references, which miss functions Ghidra never
  made - names ours instead (OwnedGlobals.cpp's redirects, now left in place). Three cases are kept apart: a compare
  with an address in a global's first 16 bytes ends the array before it and is left alone; one in the 64 bytes past a
  global ends a loop over it and is pointed past ours; a register-based access to a global of one or two words is a
  folded field or element of what surrounds it and is left alone (pointed at ours, those wrote into our image). The
  globals that no header declared are now declared (Feedback.h, GameLoop.h, WorldCamera.h, Scheduler.hpp, ...).
- **The shadows name ours.** Every literal address inside a shared global's game copy in devtools is
  `OwnedGlobals_Ours(<address>)` (or `OwnedGlobals_OursWord` where a number is wanted).
- **Vtables and callbacks.** The port stores our vtable copies and our functions where an original stores the
  game's: the owned table also lists the generated vtables (translation only), `OwnedGlobals_SameWord` /
  `OwnedGlobals_FirstDifference` / `OwnedGlobals_MatchWords` compare an original's words with the port's through
  that, and `OwnedGlobals_Canonical(Words)` puts both sides' logs and dumps in one form (a game copy's address as
  ours, a replaced original's entry as its replacement - the direction that collapses the several entries that jump
  to one function, NullFunction's among them). The byte compare helpers of 40 shadows use it.
- **Shadow bugs the move exposed** (they had written into the game's data before, harmlessly): GameAIShadowC set the
  zones' types with `I32_AT(uintptr_t(ShadowZones) + i + 0x18)`, which scales the offset by four; GameWeaponsShadowA
  the mission manager's fields the same way; GameEventsShadowD copied 16 bytes into the 12 of `StingerChannel`, over
  `InvalidatedPed` (the pedestrians then indexed with 1.0f's bits); the weapons shadows took an `A1 imm32` port
  whose address held a C3 byte for one too short to hook. InputShadow now also fakes the port's XInputSetState,
  which IFeedback::Update calls directly. GameWeaponsShadowA's fake helicopters had no physics object: their
  GetPhysicsObject is too short to hook, so the real one read a NULL and SWeaponManager::Update faulted on both
  sides 1,296 times a run (about 40 minutes of fault reports on the runner) - the fakes now hold theirs.
- **Two differences that were the tests'.** LightShadow logged path handles whose `userData` is the empty name,
  ours or the game's: its byte logs are canonical now. RoadNavShadow's InitAtPoint case 516 on mission 6 differed
  only after WorldShadow and TriggerShadow had run: a point whose grid cell has no segments leaves the original's
  roadT as the stack holds it (original-quirks.md), the port's 0.0f; the shadow clears the stack below it first.

**After the rebase onto driving-crt (9c48f4a)**, round sa5 had differences in 352 of 481 summaries on every mission
(the event shadows, the sound index, attributes, particles...), many printing the same text on both sides. Three
causes:

- **The table was partial.** owned_globals.py ran in the `preprocess` target, before `extract_driving_data` wrote
  autogenerated_vtables.h, and silently left the vtables out when that file did not exist yet - as in a checkout
  that had never built this branch. sa5's table had 833 entries instead of 1242: none of the 409 vtable copies, so
  `OwnedGlobals_Canonical`, `SameWord` and the rest no longer took our vtable copies for the game's, and every shadow
  that compares a vtable word differed. sa4 ran in the second runner checkout, whose table, from an earlier build
  there, was complete (and is what the rebased tree generates too). The script now runs after the extraction, in its target, and stops the build when an input or capstone is
  missing (it used to fall back to Ghidra's references alone, 47 redirects fewer). From the committed tree it writes
  the same table on both runner checkouts and here (byte-identical, 12,778 lines).
- **C runtime shadow B** (new to the gate: the RtlRaiseException fix came with the rebase) described image pointers
  by their address, so the port's locale implementation and thrown exceptions, which hold our vtable copies, read as
  "heap" (298 differences on every mission). Its `Where` and the thrown object's vtable check go through
  `OwnedGlobals_AsGame` now.
- **`sndsysshadow` init/restore case 4.** 9c48f4a's fix to case 0 let the loop reach case 4 (it stops at the first
  difference), where the fake output set hashes the options and vectors raw: the original's `SNDSYS_vectortoreal`
  stores dummyNullFunction (0x000d3580), the port `NullFunction` since the prep. The hash takes canonical words, and
  `OwnedGlobals_Canonical` maps dummyNullFunction to `NullFunction` as `SameWord` already did.

## What this round made ours

**Globals.** 145 more globals are ours (948 owned before, 1093 now; tools/global_coverage.py --driving: 13 ready
to own, 19 still used, 44 of unknown size, against 137, 37 and 368). All 97 zero-initialised "ready" ones, by
script; `HandsStatics`, `AIZoneData`, `GridMovers` and the other objects the static initialisers build, with
tools/static_init_driving.py taught to write their stores by name (NAMED, NAMED_BLOCKS, NAMED_STORES); the EAGL
matrices, pools and allocator hooks; the scalars with initial values (`gFeedbackAllowed`, `gStreams`, `CullDistance`,
`RandomSeed`...); and these with their initial data extracted: `SimStep`, `DefaultSystem`, the nine `ParticleType*`,
`BuiltInShapes`, `fgDamageLevels`, the weapons' instance matrix behind `IdentityMatrix`, the render methods' constant
vectors, the DSP effects image. Second `#define`s of a global in other files became `extern`s (`fgScheduler` had six).

Found on the way:

- **"GAME::SimStep" is four floats**, not one: CARP data and the EMP's render methods read a vector from it
  (`Set(1, &SimStep)`), and its fourth float is ESetFrameAnimationTime's `FrameAnimationTime`. Owned apart, the two
  would have come apart; they are one `SimStepBlock` now (render/TimeData.h), its second word a constant of the XBE.
- `AudioClock` (0x00243a6c) was owned as a `uint32_t` zeroed by Stop while EventsD and WeaponSound read it as a float.
- Three originals were still referenced. The sound fields' attribute parser 0x0006ecd0, which Ghidra has inside
  PhysicsData::Construct and no tool counted, ran: PhysicsNamespace registered it for six fields. MEM's
  block-of-pointer 0x001500a0 (no Ghidra function either) sat in MemFunctions, which nothing calls through that
  slot; `__pure_virtual` 0x00131d35 filled 91 vtable slots. All three are ported (untested): `SoundAttribParser`
  (physics/PhysicsNamespace.cpp), `MEM_blockof` (platform/RealMemory.cpp), `Crt::_purecall` (platform/CRuntime.cpp).

**Tables moved from our source to the extraction** (byte-identical to the XBE's, checked against the built DLL
first): SoftZones, ListenerPresets, WeaponSystems, BankNames, MuzzleFlashPositions, MuzzleFlashUVs,
MuzzleFlashPOVTypes, DebrisVectorsA, the six EAGL shader programs and definitions, WeaponSelectionOrder,
WeaponRefireSeconds, ExplosionTypes, MissileTypes, FxBusModes, NeedleRanges, fgCameraConstants, DriverHandIK,
BondCar_friction, BondCar_lateralLoss, EmpParam10Vectors (25). **Left in the source**: tables that read as code
(TreeLevelScale's powers of two, EmpIndices 0..47, the quads' placeholder corners), state defaults (StageCache,

functions (ProcAnimFunctions, OpcodeTable, MemFunctions...), and the generated StaticInitTable.cpp's weapon table
and `kRdata_` blocks (its generator needs capstone, which the build's Python lacks).

**Code pointers.** Every `code.pointer` and all but one `code.called`: the camera modes' update methods, CARP's
resolver table, the RCARPFile and ActManager symbol callbacks, EAGL's constructor pools, the raw pose channel
functions, the sound library's filter, mixer, reverb, stream and system hooks and its thread entry, the file system's
memory callbacks, the sync tasks, the atexit destructors, the ref counters' destroyers, the XAPI controller and time

**Vtables.** All 414 vtable literals but three now name our copies (407 vtables); an object we construct dispatches to

**Strings and constants.** `GameEmptyString` (ours, readonly), the IOModule allocation names, the EAGL render
method constants.

### Follow-ups (15 October 2026)

The three items left above are closed.

**A crash reporter** (standalone/CrashReport.h): what the loader gives the injected build, in our own code.
- CrashReport.cpp writes the report: a time-stamped heading, then the line `<exe> loaded at 0x...` (the executable is
  rebased: 0x00830000 in the test), the registers, the bytes at eip and esp, the frame chain and every return address
  on the stack, each named by its module. The loader's format with `[standalone]` for `[loader]`. Lines go to stdout,
  and each report is appended to crash.log in one write.
- CrashReportWin32.cpp catches the faults. A vectored handler reports every hard fault as it is raised, as the loader
  does. The unhandled-exception filter writes crash.dmp (the full-memory minidump) for the fault that ends the process.
  The loader writes it for the first fault: in a standalone run that is the same fault, and a fault some library
  takes care of costs no 350 MB dump.
- Closing the window now reports every other thread (`CrashReport_Threads`, the record of a freeze) and ends the
  process with HostExitProcess, as the loader does. Before, main returned with the game's thread still running.
- CrashReportPosix.cpp is the Linux body: signal handlers (SIGSEGV, SIGBUS, SIGILL, SIGFPE, SIGTRAP, SIGABRT, on an
  alternate stack). They write the same text report (registers from the ucontext, readable and executable memory from
  /proc/self/maps, module names from dladdr), then let the signal take its default course. There is no minidump and no
  thread snapshot. It compiles for i386 Linux in the nf-cross image with the HostPosix.cpp recipe (portable.md) and
  no warnings.
- `NIGHTFIRE_CRASHTEST=<ms>` (devtools/CrashTest.cpp, driving_standalone_test only) writes to address 0x10 on a
  thread of its own after that many milliseconds.
- `python tools/symbolise.py --map Release/driving_standalone_test.map crash.log` names our functions. It rebases the
  map by the report's "loaded at" line, and `--base module=0x...` gives a base the report lacks. The same works for
  the injected build's DLL, with drivinginject.map and the drive log, where the loader prints the DLL's base.
  Undecorated names are shortened (`Scheduler::Run`, `` `anonymous namespace'::Fault ``). symbolise.py also had a
  bug: its pattern only matched XBE addresses below 0x00100000. It now names any address in the image, except in a
  standalone report.
- The test (runner, mission 1, 15 s): the report and a 343 MB crash.dmp. Symbolised, the report reads Fault+0x6,
  FaultCaller+0xd, CrashThread+0x34.

**Shadow coverage for the C++ library's last ports**: two new parts of CRuntimeShadowB, beside the old ones.
- "strstreambuf virtuals" covers overflow, pbackfail, underflow, seekoff and seekpos (and fpos(streamoff) through
  them). It uses ten buffer layouts over a lent text, eight _Strstate modes and the characters each function treats
  apart. Overflow is tried with operator new[] (the new block lent while it is described), with a recording
  allocator over a lent arena, and with a recording free function, at five allocation sizes, one of them too big for
  the arena. Seekoff and seekpos get every way and openmode, with positions inside and outside the buffer.
- "other virtuals" covers the deleting destructors of exception, bad_cast, runtime_error, ios_base::failure,
  type_info and `_Locimp` (with fake facets whose references run out), each in place (flags 0) and on the heap
  (flags 1). It also covers the copy constructors and destructors of bad_cast, runtime_error and failure, the two
  what()s, failure's `_Doraise` (the throw caught and compared) and the deleting destructors of a basic_ostream and an
  ostrstream entered at their basic_ios.
- Two input classes are left out: they fault on both sides alike. A dynamic buffer with a get area and no put area
  sizes its growth from a null pointer, and copying an exception that owns a null message calls strlen on it.
- A mutated build showed the parts can see a difference: pbackfail returning the character unmasked, and
  exception::what's default string one letter short. Both were caught (60 and 3 differences).
- One finding, fixed: `~basic_ostream`'s vbase destructor (0x00131a06) is entered at the basic_ostream (its one
  caller, the deleting destructor 0x001319e7, passes this - 4). The port had taken it at the basic_ios. It is
  `Ostream::DestructAll` now. Nothing reached it by the original's address (Ghidra: that one caller, now ours), so no
  behaviour changed.
